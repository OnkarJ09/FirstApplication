[HIGH-001] Data Extraction via ADB Backup (allowBackup="true")

Severity: HIGH CVSS: 5.9 CWE-926 OWASP: MASVS-STORAGE-1
Physical Confirmation Prompt Triggered via ADB

🔍 How We Found It

Static manifest auditing with APKTool identified android:allowBackup="true" declared on line 4 of AndroidManifest.xml. We verified physical exploitability over USB debugging by invoking the backup bridge:

adb backup -f backup.ab com.onkar.androidtest

The connected phone immediately intercepted the call and presented the full-screen prompt shown on the left: "Full backup — A full backup of all data to a connected desktop computer has been requested..."

💡 Technical Explanation & Attack Impact

When android:allowBackup is set to true, any physical workstation with developer access can trigger an ad-hoc serial snapshot of the application's sandboxed storage directory (/data/data/com.onkar.androidtest/) without requiring root privileges.

# Attack Exfiltration Sequence:
dd if=backup.ab bs=24 skip=1 | zlib-flate -uncompress > backup.tar
tar -xf backup.tar
# Local SQLite DBs, Shared Preferences, and tokens are extracted.

Even though the initial release does not store sensitive credentials, leaving this enabled creates immediate data leak vulnerability the moment tokens or sensitive cache files are added.

🛠️ Way to Fix It (Remediation)

Explicitly disable ADB serialization within AndroidManifest.xml:

<application
    android:allowBackup="false"
    ... >

If automated Google Cloud user migration is strictly necessary, supply a scoped filtering rule:

<!-- res/xml/backup_rules.xml -->
<full-backup-content>
    <exclude domain="database" path="."/>
    <exclude domain="sharedpref" path="."/>
    <exclude domain="file" path="."/>
</full-backup-content>

[MED-001] Exported ProfileInstallReceiver with System Permission

Severity: MEDIUM CVSS: 4.3 CWE-926 OWASP: MASVS-PLATFORM-2

🔍 How We Found It

Manifest disassembly exposed an exported broadcast listener protected by a signature-level system permission:

<receiver android:name="androidx.profileinstaller.ProfileInstallReceiver" 
          android:exported="true" 
          android:permission="android.permission.DUMP">
    <intent-filter>
        <action android:name="androidx.profileinstaller.action.INSTALL_PROFILE"/>
    </intent-filter>
</receiver>

We confirmed component accessibility via ADB broadcast invocation:

adb shell am broadcast -a androidx.profileinstaller.action.INSTALL_PROFILE \
  -n com.onkar.androidtest/androidx.profileinstaller.ProfileInstallReceiver
# Broadcast completed: result=0

💡 Technical Explanation & Attack Impact

This receiver originates from Google's AndroidX ProfileInstaller library, intended for AOT compilation optimization benchmarking. While protected by android.permission.DUMP (preventing normal user apps from triggering it), it remains an open IPC target for shell or privileged device processes, presenting an unnecessary attack surface for Denial of Service (DoS) or benchmark manipulation.

🛠️ Way to Fix It (Remediation)

If production benchmarking is not required, strip the dependency or suppress it through manifest merger:

<!-- AndroidManifest.xml -->
<receiver
    android:name="androidx.profileinstaller.ProfileInstallReceiver"
    tools:node="remove" />

[LOW-001] Resources Confusion (R8 Artifact)

Severity: LOW CVSS: 2.1 CWE-693

🔍 How We Found It

Running APKiD against the package identified a known bytecode manipulator signature:

apkid app-release.apk
# |-> manipulator : Resources Confusion (classes.dex)

💡 Technical Explanation

This is an aggressive R8 optimization technique that scrambles resource tables and IDs to reduce binary size. While it slows down reverse engineering, it can trigger resource loading crashes or collisions on custom Android ROMs (OneUI, HyperOS).

🛠️ Way to Fix It

Verify UI rendering across real hardware. If crashes occur, add resource retention exceptions inside proguard-rules.pro.

[LOW-002] Missing Network Security Config

Severity: LOW CVSS: 3.7 CWE-319

🔍 How We Found It

Decompiled directory inspection verified that res/xml/network_security_config.xml is absent, and the manifest contains no configuration declaration.

💡 Technical Explanation

Although the APK currently declares no android.permission.INTERNET, adding API connectivity in future versions without this file leaves communication open to cleartext HTTP fallback or rogue root CAs on pre-Android 9 devices.

🛠️ Way to Fix It

Add res/xml/network_security_config.xml:

<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors><certificates src="system"/></trust-anchors>
    </base-config>
</network-security-config>

Reference it in AndroidManifest.xml:

<application android:networkSecurityConfig="@xml/network_security_config" ... >

Optimizer

Found: APKiD flagged DEX as "r8 without marker".

Explanation: Normal minification for release builds where compilation annotations are stripped to compress binary footprint.

Fix: No action required.

[INFO-003] Certificate Validity

27 Years

Found: keytool reported signing validity until February 11, 2054.

Explanation: Long lifespans allow smooth updates, but 27-year validity extends the window of risk if private keystores are compromised.

Fix: Standardize on 10–15 year certificate expiry for production releases.
